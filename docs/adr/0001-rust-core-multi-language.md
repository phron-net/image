# 0001. One Rust core, a binding per language, one repository

Status: accepted, 2026-11-12.

## Context

The Phron Image SDK builds and signs image URLs. The server verifies a signature byte for byte, so
every language must produce the same string for the same input. A second implementation per
language means a second place for a signing bug.

## Decision

- **One repository for every language.** `phron-net/image` holds the whole SDK. Packages are named
  per product: npm `@phron/image`, PyPI `phron-image`, Go under `github.com/phron-net/image/go`,
  crates.io `phron-image`.
- **Rust is the single implementation.** `crates/phron-image` has the options, path encoding,
  signing and URL grammar. It does no I/O. Each language gets it through a binding:
  `bindings/node` (napi-rs) now; Python (pyo3, maturin) and Go later.
- **Conformance vectors.** `conformance/vectors.json` is generated by `conformance/generate.ts`
  from an implementation that shares no code with the SDK (`node:crypto`, `encodeURIComponent`).
  The Rust test and every binding's test run it.
- **Releases with Sampo.** One changeset per change; `sampo release` bumps `@phron/image` and its
  CHANGELOG; the workflow tags `v<version>`; the tag runs the build matrix and the npm publish.
  The workflow headers (`.github/workflows/release.yml`, `publish-npm.yml`) describe each step.

## Consequences

- **Two napi targets, decided 2026-11-12.** napi-rs builds the binding twice from one crate:
  native for `x86_64-unknown-linux-gnu`, where servers run and speed matters, and threadless
  WebAssembly (`wasm32-wasip1`) for every other host. Each native target would be one more npm
  platform package and trusted publisher, so other platforms take the WebAssembly build instead
  of their own binaries. The release is three npm packages: `@phron/image`,
  `@phron/image-linux-x64-gnu` and `@phron/image-wasm32-wasip1`. The WebAssembly package has
  no `cpu` restriction (`napi.wasm.cpu: false`), so it installs everywhere and the Node loader
  falls back to it when no native binary loads.
- **No second binding.** wasm-bindgen was considered and rejected: it is a second binding to
  keep in step with the napi one (napi-rs v3 announcement, "Why don't use wasm-bindgen
  instead"). No language package is written by hand.
- **Cloudflare Workers** run the WebAssembly build through napi-rs's deferred workerd loader
  (`@phron/image/workerd` with `@phron/image/wasm`), which takes a precompiled
  `WebAssembly.Module` because Workers forbid compiling WebAssembly from bytes. CI runs the
  vectors inside workerd. The same loader serves Deno (the module compiled from `./wasm.wasm`'s bytes)
  and Vercel Edge (a `?module` import). `verify-published.yml` runs the vectors against the
  package installed from npm in workerd, Deno 2.9 and Vercel's `edge-runtime` emulator after
  each publish; a live Deno Deploy or Vercel deployment is not tested.
- The Next.js `publicLoader` is plain TypeScript, pinned to the core by the `public`
  conformance vectors; it is retired once the browser entry of the WebAssembly build serves it.
- `signUrl` is synchronous (it was async over Web Crypto), and the `./node` subpath is gone.
